# Meepo — ТЗ

> Один игрок. Много агентов. Жми Tab.

Нативное macOS-приложение для управления несколькими сессиями Claude Code по разным проектам и задачам. Заменяет связку «VS Code + много окон + терминал в каждом». Открытый исходный код, установка через Homebrew.

Язык: русский для текста, английский для кода, коммитов и README.

---

## 0. Как работать с этим ТЗ (для Claude Code)

- Собираем **по модулям, строго по порядку** (раздел 6). Каждый модуль должен работать сам по себе, прежде чем начинать следующий.
- Перед каждым модулем: `/plan` → подтверждение пользователя → реализация → `/qa` → `/ship`.
- В конце каждого модуля: `/sync`, чтобы следующая сессия начала с полным контекстом.
- Если что-то в ТЗ противоречит реальному поведению Claude Code (формат файлов, поля хуков, флаги CLI) — **сначала проверь по документации и реальным файлам**, потом сообщи пользователю и предложи правку ТЗ. Не выдумывай API.
- Пользователь не пишет код сам. Объясняй решения коротко и по делу.

### Шаг 0: репозиторий
```bash
gh repo create meepo --public --description "Tab through your Claude Code agents" --clone
```
Положи этот файл в репозиторий как `SPEC.md`. Создай `CLAUDE.md` со стеком, командами сборки и ссылкой на `SPEC.md`.

## 1. Проблема

Пользователь ведёт несколько проектов параллельно через Claude Code:

1. Каждое утро открывает каждый проект вручную: окно VS Code, терминал, `claude`. Долго.
2. Уведомления не говорят, какая сессия и что ей нужно.
3. Две фичи в одном репозитории конфликтуют, агенты путаются.
4. Удачные практики (команды, хуки) живут в одном проекте и не переезжают в другие.
5. Ритуал `sync → simplify → ship` забывается.
6. Сессии перезапускаются ради чистого контекста, и теряется учёт токенов за день.
7. Непонятно, когда пора синхронизировать память и начинать новую сессию.
8. Docker копит образы, порты конфликтуют, диск забивается.
9. Скриншоты сохраняются файлами, хотя нужны только чтобы вставить в сессию.
10. CI/CD приходится проверять руками.
11. Сессия ждёт «accept», пока пользователя нет у компьютера.
12. Логи с серверов по SSH приходится собирать руками.
13. В конце дня нет общей картины: что сделано и что осталось по каждому проекту.

## 2. Суть решения

Meepo — пульт управления сессиями: одно окно со всеми сессиями + иконка в строке меню + Telegram-бот как пульт с телефона.

Замкнутый цикл дня:
**задачи утром → запуск сессий → работа по этапам → итоги вечером → задачи на завтра.**

## 3. Принципы

- **Адаптивность.** Ничего не хардкодить под одного пользователя: команды читаются из `.claude/commands/`, стадии CI из воркфлоу, серверы из `~/.ssh/config`.
- **Не ломать чужой сетап.** Meepo добавляет свой хук-мост рядом с существующими хуками пользователя. Любое изменение `settings.json` — с бэкапом и возможностью откатить.
- **Локально.** Никаких своих серверов. Всё работает на машине пользователя. Телеметрии нет.
- **Безопасно по умолчанию.** Никаких пушей в main/master, force push, автопочинки деплоя без явного разрешения.
- **Экономия токенов.** Логи режутся до упавших шагов, контекст передаётся выжимкой.

## 4. Архитектура

### Стек
- **Swift + SwiftUI**, macOS 14+. Окно приложения + `MenuBarExtra` для иконки в строке меню.
- **SwiftTerm** — встроенные терминалы, в которых живут сессии `claude`.
- **SQLite (GRDB)** — локальная база: проекты, сессии, токены, задачи, события.
- **Локальный HTTP-сервер** на `127.0.0.1` (Network.framework) — приём событий от хуков.
- **WidgetKit** — виджет рабочего стола (последний модуль).
- Внешние CLI: `claude`, `git`, `gh`, `ssh`, `docker`. Meepo вызывает их, а не переписывает их логику.

### Три источника данных

1. **Хук-мост.** Один скрипт `meepo-bridge.sh`, подписанный на все события Claude Code (`SessionStart`, `Notification`, `Stop`, `PreToolUse`, `PostToolUse`, `PreCompact` и др.). Пересылает JSON события в Meepo:
   ```bash
   #!/bin/bash
   curl -s -m 2 -X POST "http://127.0.0.1:${MEEPO_PORT:-47800}/event" \
     -H "Content-Type: application/json" --data-binary @- >/dev/null 2>&1
   exit 0
   ```
   Исключение — режим удалённых подтверждений (модуль 6): там мост ждёт ответа от Meepo.
   Если Meepo не запущен, мост молча завершается и ничего не ломает.

2. **JSONL-файлы сессий** в `~/.claude/projects/`. Источник токенов (поле `usage` у ответов модели: input, output, cache creation, cache read), модели, времени. Парсер должен быть терпим к изменениям формата: неизвестные поля игнорировать, ошибки логировать, не падать.

3. **Файлы проекта**: `.claude/commands/`, `.claude/settings.json`, `CLAUDE.md`, `.github/workflows/`, `git`.

### Сущности
- **Project** — папка с git-репозиторием, имя, remote, цвет, порт-диапазон.
- **Session** — сессия Claude Code: проект, worktree/ветка, модель, этап, статус, id сессии Claude, заполненность контекста.
- **Task** — задача: текст, проект, статус, контекст (заметки, ссылки, файлы).
- **Event** — событие от хука.
- **UsageRecord** — токены: сессия, модель, день, тип токенов.
- **Server** — SSH-хост из `~/.ssh/config` + привязка к проекту.

### Статусы сессии
`thinking` · `waiting_input` · `waiting_permission` · `idle` · `needs_sync` · `error`

## 5. Интерфейс и стиль

### Главное окно
- **Слева** — «юниты»: карточки сессий, сгруппированные по проектам. У каждой карточки:
  - портрет в рамке (иконка проекта);
  - имя проекта и ветка;
  - **полоска контекста** (как полоска здоровья: зелёная → жёлтая → красная);
  - этап (план / код / QA / ship / sync);
  - статус и счётчик токенов за сегодня.
- **Центр** — терминал выбранной сессии.
- **Справа (сворачивается)** — лента событий, задачи проекта, CI, серверы.

### Горячие клавиши
- `Tab` / `Shift+Tab` — следующая / предыдущая сессия.
- `Ctrl+Tab` — сразу к следующей сессии, которая ждёт пользователя.
- `Cmd+1..9` — сессия по номеру.
- `Cmd+N` — новая сессия.
- Глобальный хоткей для скриншота (модуль 8), настраивается.

Внимание: `Tab` внутри терминала нужен для автодополнения. Переключение по `Tab` работает, когда фокус на списке сессий; из терминала — по `Ctrl+Tab` или настраиваемому сочетанию. Решить это в модуле 1 и показать пользователю варианты.

### Иконка в строке меню
- Бейдж — число сессий, которые ждут пользователя.
- Клик — компактная панель: сессии со статусами, токены за день, кнопка «открыть Meepo».

### Стиль
- Эстетика рисованных RTS начала 2000-х: ручные текстуры, коренастые формы, каменные рамки с золотой окантовкой у портретов, насыщенные цвета.
- Палитру пользователь задаёт сам по своим референсам. Все цвета — через дизайн-токены в одном файле, чтобы их можно было поменять разом. Стартовая палитра-заглушка: тёмный камень `#1B1F24`, мох `#4E7A3A`, золото `#C9A24A`, бирюзовое свечение `#3FB8AF`, огонь `#E0762F`.
- **Запрещено:** персонажи, иконки, звуки и любые ассеты из Dota/Warcraft или других игр. Только оригинальная графика.
- Светлая и тёмная темы.

## 6. Модули (порядок сборки)

Каждый модуль: что делает → критерии готовности.

### Модуль 1. Ядро
- Приложение-окно + иконка в строке меню.
- Добавление проектов (выбор папки, автоопределение git remote).
- Запуск сессии: встроенный терминал в папке проекта, команда `claude` с нужными флагами (модель, начальный промпт, продолжение сессии — сверить флаги с `claude --help`).
- Список сессий, переключение по горячим клавишам.
- Сессии переживают перезапуск Meepo (восстанавливаются через продолжение сессии Claude Code).

**Готово, когда:** можно добавить 3 проекта, запустить в каждом сессию, переключаться между ними с клавиатуры и ни разу не открыть VS Code.

### Модуль 2. События и уведомления
- Установка хук-моста в `~/.claude/settings.json` с бэкапом, рядом с существующими хуками. Кнопка «удалить мост».
- Статусы сессий по событиям в реальном времени.
- Уведомления macOS с **проектом, веткой и текстом**. Клик по уведомлению открывает нужную сессию.
- Лента событий, включая заблокированные защитными хуками действия.

**Готово, когда:** по уведомлению сразу понятно, какая сессия и что ей нужно, а клик ведёт прямо в неё.

### Модуль 3. Токены и контекст
- Парсинг JSONL, агрегация по дню, проекту, сессии, модели.
- Учёт **не сбрасывается** при перезапуске сессий.
- Заполненность контекста каждой сессии (по последнему ответу модели относительно окна контекста модели; размеры окон — в настройках).
- Экран статистики: сегодня / неделя / по проектам / по моделям.

**Готово, когда:** после трёх перезапусков сессий за день итог токенов за день совпадает с суммой по JSONL.

### Модуль 4. Этапы и эстафета сессий
- Панель команд строится из `.claude/commands/` проекта (и глобальных из `~/.claude/commands/`). Пользователь один раз задаёт порядок этапов, например: `plan → код → qa → security → simplify → ship → sync`.
- У сессии виден текущий этап, следующий подсвечивается.
- Модель по этапу: например, `plan` на одной модели, реализация на другой. Настраивается.
- Передача плана: план готов → кнопка «в реализацию» → новая сессия на модели реализации с планом во входном контексте.
- Индикатор «пора sync»: порог заполненности контекста (по умолчанию 70%) → предложение. Кнопка «эстафета»: `/sync` в текущей сессии → новая чистая сессия в том же проекте и ветке → старая закрывается.
- Напоминания: «есть незакоммиченные изменения», «qa не запускался».

**Готово, когда:** сессию на 75% контекста можно одной кнопкой заменить свежей, которая продолжает ту же задачу.

### Модуль 5. Параллельные фичи и порты
- Вторая сессия в том же проекте по умолчанию создаёт **git worktree** с отдельной веткой в `~/.meepo/worktrees/<project>/<branch>`.
- После мержа ветки — предложение удалить worktree.
- Каждый проект/worktree получает свой диапазон портов. Переменные (`PORT`, `MEEPO_PORT_BASE`) пробрасываются в окружение сессии.
- Список занятых портов с указанием процесса.

**Готово, когда:** две фичи в одном репо разрабатываются параллельно без конфликтов файлов и портов.

### Модуль 6. Telegram-бот
Бот пользователя (токен от @BotFather в настройках), long polling, без сервера.
- **Уведомления** с проектом, веткой, текстом.
- **Удалённые подтверждения:** режим «я отошёл». Хук-мост на `PreToolUse` отправляет запрос в Meepo и ждёт решения; Meepo пересылает в Telegram с кнопками «Разрешить / Отклонить». По таймауту — вернуть обычный запрос в терминал. Сверить механизм решения хука (allow / deny / ask) с актуальной документацией хуков. Отвечать боту может только chat id владельца.
- **Задачи:** пересланное или написанное боту сообщение = список задач. Meepo раскладывает задачи по проектам (по названиям и ключевым словам, с подтверждением пользователя).
- **Статус:** команда `/status` — сессии, этапы, токены за день.

Проверить и описать в README: встроенный удалённый доступ Claude Code через мобильное приложение Claude — чем Meepo отличается и не дублирует ли.

**Готово, когда:** с телефона можно увидеть, что сессия ждёт, прочитать запрос и разрешить его.

### Модуль 7. Утро и вечер
- **Утренний запуск:** список задач (из бота или вставкой) → распределение по проектам → одна кнопка запускает все сессии, каждая с задачей в первом промпте.
- **Итоги дня:** по каждому проекту — коммиты, пройденные этапы, токены, TODO/FIXME, которые агент оставил в коде (из событий `PostToolUse`), следующие шаги из последнего `sync`/`retro`.
- **To-do по проектам:** добавить задачу руками, привязать к ней контекст (заметка, ссылка, файл, скриншот). Незакрытые задачи переходят в утренний запуск.
- Экспорт итогов в Telegram одним сообщением.

**Готово, когда:** вечерний список завтра утром превращается в запущенные сессии одной кнопкой.

### Модуль 8. Скриншоты
- Глобальный хоткей → выделение области → всплывающая миниатюра со списком сессий → выбор (стрелками/Tab) → картинка отправляется в выбранную сессию.
- Файлы временные, Meepo удаляет их через N часов.
- Разрешение «Запись экрана» — с понятным объяснением при первом запуске.

**Готово, когда:** скриншот попадает в нужную сессию за 2 нажатия и не остаётся на рабочем столе.

### Модуль 9. CI-страж
- Через `gh`: запуски воркфлоу по всем проектам, джобы и шаги. Стадии берутся из реальных воркфлоу, не хардкодятся.
- Статус CI на карточке сессии.
- При падении:
  1. один раз перезапустить упавшие джобы (флейки);
  2. снова красное → логи **только упавших шагов**;
  3. сессия Claude Code в проекте с контекстом: воркфлоу, ветка, коммит, лог; фикс идёт в отдельную ветку + PR;
  4. лимит попыток (по умолчанию 3);
  5. итог — уведомление.
- Воркфлоу деплоя по умолчанию **не чинятся автоматически**, только уведомление. Включается отдельно для каждого проекта.
- Архитектура провайдеров: сначала GitHub Actions, интерфейс готов под GitLab CI и др.

**Готово, когда:** упавший CI в любом проекте без участия пользователя превращается в PR с фиксом или в понятное уведомление, почему не удалось.

### Модуль 10. Серверы и логи (SSH)
- Список хостов из `~/.ssh/config` + ручное добавление. Привязка сервера к проекту (один проект — несколько серверов: prod, stage).
- Meepo **не хранит ключи**: использует системный `ssh` и ssh-agent.
- **Источники логов на сервер** настраиваются шаблонами: `journalctl -u <service> -n 200`, `docker logs --tail 200 <container>`, `tail -n 200 <file>`. Для Docker — список контейнеров на сервере одной кнопкой.
- Кнопка «логи → в сессию»: логи за выбранный период уходят в сессию проекта (или в новую, с командой `/investigate`), с обрезкой до разумного размера.
- При падении деплоя в CI-страже — предложить подтянуть логи с сервера этого проекта.
- **Только чтение по умолчанию.** Любые команды, кроме заданных шаблонов чтения логов, — только с явного подтверждения пользователя.

**Готово, когда:** «что-то не так на проде» → два клика → свежие логи с нужного сервера в сессии Claude с командой расследования.

### Модуль 11. Библиотека практик и Docker
- **Библиотека:** глобальные команды, хуки и правила в одном месте (`~/.claude/` + репозиторий-библиотека по желанию). Показывает, какие проекты используют устаревшую копию команды, и предлагает обновить. Если в проекте появилась новая команда или правка — предлагает поднять в библиотеку.
- **Docker:** занятое место (`docker system df`), висящие образы и контейнеры по проектам, чистка одной кнопкой с подтверждением.

**Готово, когда:** правка `ship.md` в библиотеке доходит до всех проектов одной кнопкой.

### Модуль 12. Релиз-ноуты
- После `ship`: черновик поста в Telegram-канал на основе коммитов и отчёта ship.
- Стиль: пользователь даёт 5–10 примеров своих постов; они хранятся как образцы стиля.
- Одобрение в Telegram кнопкой → публикация в канал через бота (бот — админ канала).
- Привязка канала к проекту.

### Модуль 13. Полировка и запуск
- Виджет рабочего стола: токены за день, число активных сессий, ждущие сессии.
- Онбординг: проверка `claude`, `gh`, `git`, `docker`, установка моста, выбор проектов.
- Иконка, маскот (оригинальный персонаж), скриншоты для README и Product Hunt.
- README на английском: что это, GIF-демо, установка, настройка Telegram, безопасность.

## 7. Установка и дистрибуция
- Сборка `.app`, публикация в GitHub Releases через CI.
- Свой tap: репозиторий `homebrew-meepo` с cask. Установка:
  ```bash
  brew tap <user>/meepo
  brew install --cask meepo
  ```
- Подпись и нотаризация Apple — при наличии Apple Developer аккаунта ($99/год). Без неё — инструкция в README, как открыть приложение при первом запуске.
- Автообновление: Sparkle или проверка GitHub Releases.

## 8. Безопасность
- HTTP-сервер слушает только `127.0.0.1`, запросы с локальным токеном из `~/.meepo/token`.
- Telegram: реагировать только на chat id владельца.
- Секреты (токен бота) — в Keychain.
- Никогда: push в main/master, force push, автопочинка деплоя без флага, команды на серверах кроме шаблонов чтения, чтение `.env` для отправки куда-либо.
- Все действия Meepo, меняющие файлы пользователя, пишутся в лог и откатываемы.

## 9. Вне рамок первой версии
- Linux и Windows.
- Другие агенты кроме Claude Code (архитектуру не закрывать под это).
- Встроенный редактор кода и просмотр диффов сверх базового.
- Автопроверка в браузере (у пользователя уже есть команда `/qa` через Chrome — Meepo только напоминает её запускать).

## 10. Контекст пользователя (для понимания воркфлоу)
Существующие команды: `plan`, `investigate`, `qa`, `security`, `ship`, `sync`, `retro`, `updates` (+ встроенная `simplify`).
Существующие хуки: `notify-macos`, `pre-bash-safety`, `protect-env`, `commit-msg-validate`, `session-context`, `stop-verify`, `pre-compact-snapshot`, `todo-tracker`.
Модели: план — самая сильная модель с максимальным режимом рассуждения; реализация — модель по умолчанию.
Meepo должен работать с этим сетапом «из коробки», но не зависеть от него: у другого пользователя может не быть ни одной из этих команд.
